# Ball Split — 分裂ボール・シミュレーション

密閉された円形アリーナの中で、2 個のボールが等速でランダムな方向に動き回る。
ボール同士が接触すると両方が 2 個に分裂し、数が 2 → 4 → 8 … と指数的に増えていく。
2^16 = 65536 個に達した時点で停止する。

インターンシップ課題 2（自由課題）の提出物。

## 動かし方

### macOS

SDL2 が必要。Homebrew で入れる。

```
brew install sdl2
make
./ballsim
```

### Windows

ビルド済みの exe を [Releases](https://github.com/mocaluna0117/ball-split/releases/tag/v1.0) に置いてある。
`BallSplit-windows-x64.zip` を展開して `ballsim.exe` をダブルクリックする。

| ファイル | 中身 | 使い方 |
|---|---|---|
| `ballsim.exe` | 単体で動く版 | そのまま実行する。DLL は不要 |
| `fallback/` | `ballsim.exe` と `SDL2.dll` | 上が動かない時の予備。2 つを同じ場所に置く |

単体版は SDL2 も C++ ランタイムも exe の中に取り込んであり、依存しているのは
Windows に標準で入っている DLL だけ。macOS 上で MinGW-w64 によりクロスコンパイルしたもので、
**Windows 11（64 ビット）の実機で動作を確認している**（Windows 10 は未確認）。

#### Windows 上でビルドし直す場合（Visual Studio）

CMake で Visual Studio のソリューションを生成する。`.sln` には生成した PC の絶対パスが
入るため、リポジトリには含めていない。vcpkg を使う場合は次のとおり。

```
vcpkg install sdl2:x64-windows
cmake -S . -B build -G "Visual Studio 17 2022" -A x64 -DCMAKE_TOOLCHAIN_FILE=<vcpkg>/scripts/buildsystems/vcpkg.cmake
cmake --build build --config Release
```

`build/ballsim.sln` を Visual Studio で開いてビルドしてもよい。
Visual Studio 2022 の「フォルダーを開く」で、このフォルダを直接開くこともできる。
（Windows 11 と macOS でビルドが通ることを確認済み）

vcpkg を使わない場合は、SDL2-devel-<version>-VC.zip を展開してその場所を渡す。

```
cmake -B build -S . -DSDL2_ROOT=C:/SDL2-2.32.10
cmake --build build --config Release
```

どちらも `SDL2.dll` は exe の隣に自動でコピーされる。

#### macOS からクロスビルドする場合

```
brew install mingw-w64
# SDL2-devel-<version>-mingw.tar.gz を展開しておく
SDL2_MINGW=<展開先>/SDL2-2.32.10/x86_64-w64-mingw32 ./build_windows.sh
```

`dist/windows` と `dist/windows-dll` の両方が作り直され、
依存 DLL の一覧が表示される。Windows 標準以外の名前が出たら同梱が必要という意味。

## 操作

| 操作 | 内容 |
|------|------|
| Space / START ボタン | 開始・一時停止 |
| R / RESET ボタン | いまの初期個数で配置し直し、開始前の状態に戻す |
| ↑↓ / SPEED の +− ボタン | シミュレーション速度 1x 〜 512x（起動時は 16x） |
| ←→ / INITIAL の +− ボタン | 初期配置の個数 2 〜 8192（変更すると即座に配置し直す） |
| Esc | 終了 |

初期個数が 2 の時は最初の接触まで時間がかかる。速度を上げて早送りするか、
初期個数を増やすとすぐに連鎖が始まる。

### コマンドライン

```
./ballsim --initial 256                 # 初期個数を指定して起動
./ballsim --headless                    # 画面なしで最後まで回し、到達時間と検証結果を出す
./ballsim --headless --initial 4096     # 初期個数を変えて検証
./ballsim --shot out.bmp                # 上限到達時の 1 フレームを画像に保存（資料用）
./ballsim --shot out.bmp --shot-at 30   # 30 フレーム目を保存
```

Windows ではウィンドウアプリとしてビルドしているので、ダブルクリックしても
コンソールは開かない。`--headless` をコマンドプロンプトや PowerShell から実行した時だけ、
呼び出し元の画面に結果が出る（プロンプトが先に戻り、結果はその後ろに表示される）。

## 仕組み

### データ

ボールは `struct Ball { float x, y, vx, vy, cooldown; }` の配列。
速度の大きさは常に一定で、向きだけが変わる。

### 初期配置

指定された個数を円の中にランダムに撒く。細かいが効いている点が 3 つある。

中心からの距離には乱数の平方根をかけている。そのまま乱数を使うと中心付近に偏るため。
円の面積は半径の 2 乗に比例するので、一様に散らすには平方根が要る。

撒く範囲は個数に応じて広げる。少数なら中心寄り、多数ならアリーナ全体に近づく。

初期ボールには分裂の猶予を最初から与えている。ランダムに置く以上まれに重なるが、
猶予があれば置いた瞬間に分裂してしまうことがなく、切れる前に押し戻しで離れる。

### 1 ステップの流れ

```
位置を進める → 衝突を解決 → 壁を解決 → 衝突を解決 → 壁を解決
```

衝突と壁を 2 巡するのは、壁の押し戻しがボールを内側へ動かす際に新しい重なりを
作ってしまうため。1 巡で終えるとその重なりが直されないまま画面に出る。
2 巡目では分裂させない（分裂は 1 ステップにつき 1 回まで）。

### 壁の反射

円の中心からボールへ向かう向きが、そのまま壁の法線 `n` になる。
中心からの距離が `R - r` を超えたら、その位置まで戻してから速度を鏡面反射させる。

```
v' = v - 2(v・n)n
```

`v・n > 0`、つまり外向きに動いている時だけ反転させる。これを省くと押し戻した直後に
内向きの速度まで反転してしまい、壁に貼り付いて震える。

### ボール同士の衝突

中心間の距離が直径より近ければ接触。判定は 2 乗のまま比較して平方根を避けている。

- めり込み量を半分ずつ分け合って引き離す
- 質量が等しい弾性衝突なので、法線方向の速度成分をそっくり交換する
- 交換後に速さを一定値へ揃え直す

最後の「速さを揃え直す」は物理的には正しくない。エネルギーを勝手に出し入れしている。
それでもこうするのは、速さがばらつくと遅いボールが次の接触をなかなか起こさず、
連鎖が失速してしまうため。見た目の一貫性と、上限まで増えきることを優先した妥協。

### 分裂

接触した 2 個のうち両方が猶予切れで、かつ上限に余裕があれば分裂させる。

- 親の位置からランダムな軸に沿って `±r` だけずらした位置に子を 2 個置く
- 子は分裂直後 0.25 秒のあいだ再分裂しない。これが無いと生まれた瞬間に連鎖して一瞬で上限に達する
- 親のスロットを子 1 で上書きし、子 2 だけ末尾に追加する。要素の削除が起きない

分裂はその場では行わず、番号を記録しておいて走査が完全に終わってから適用する。
走査中に `std::vector` へ追加すると、再確保で保持中の参照が無効になり、さらに
`size()` が増えてループ条件まで壊れるため。

### 空間分割（この課題の中心）

総当たりだと調べるペアは n(n-1)/2 で、65536 個では 1 ステップあたり約 21 億組になる。
毎秒 480 ステップ動かすので、これは不可能。

そこで空間をボールの直径と同じ幅のマス目に区切る。接触しうる相手は自分のマスと
周囲 8 マスの中にしかいないので、離れたマスは見に行かなくてよい。

マスへの登録は配列 2 本で「鎖」を作る方式にした。

```
cellHead[c]   マス c の先頭のボール番号（空なら -1）
nextBall[i]   ボール i の次のボール番号（終端なら -1）
```

登録は 2 行で済み、マスがいくら増えてもメモリはボールの数ぶんしか要らない。
毎ステップ全マス（446 × 446 = 約 20 万）を初期化すると書き込みが無駄になるので、
使ったマスの番号を `occupiedCells` に控えておき、そこだけ戻す。

走査では隣を 8 方向ではなく右・左下・下・右下の 4 方向だけ見る。
こうすると隣り合うどの 2 マスについても片方だけが相手を調べる形になり、
同じペアを 2 回処理するのを防げる。同じマスの中でも鎖の自分より後ろだけを見る。

### 描画

65536 個の矩形を `SDL_RenderFillRectsF` に一括で渡し、描画呼び出しを 2 回
（通常色と分裂直後の色）に抑えている。文字は外部ライブラリを使わず、
5x7 のビットマップフォントをドット単位の矩形として描いている。

重い時はフレーム内の物理計算を 12 ミリ秒で打ち切る。速度倍率が自動的に下がるだけで、
描画は 60fps を保ったまま破綻しない。HUD の EFF がその実効倍率。

## 検証

`./ballsim --headless` で GUI なしに最後まで回し、次を確認している。

| 項目 | macOS / Apple M2（16 回実行） | Windows 11（1 回実行） |
|------|------|------|
| 到達数 | 65536 / 65536 | 65536 / 65536 |
| アリーナ外に出たボール | 0 個 | 0 個 |
| 重なっているペア（ボール数に対する割合） | 4〜8% | 6.2% |
| 最も深い重なり | 0.21〜0.55 px、中央値 約 0.30 px | 0.27 px |
| 上限時の 1 ステップ | 約 8 ミリ秒 | 7.24 ミリ秒 |

判定基準は、最も深い重なりが 1.0 px 未満であること。

重なりの基準を割合ではなく絶対値にしているのは、画面が論理 1000px を 900px のウィンドウに
描くため、1.0 論理 px が実画面で 0.9 ピクセルに相当するからである。
「1 ピクセルもずれて見えない」が基準の意味。最大値は 65536 個の中の最悪値なので
実行ごとに揺れる性質があり、基準は測定した最大に対して 2 倍近い余裕を取ってある。

初期個数を 2 / 256 / 4096 に変えた場合もそれぞれ上限まで到達することを確認している。

## 残っている妥協点

- 重なりが完全にはゼロにならない。反復回数を増やせば減らせるが、その分だけ遅くなる。
  現状は画面で見えない大きさに収まっているため、そこで止めている。
- 上限に近づくと 1 ステップが 7〜8 ミリ秒かかる。実時間で進めるには 1/480 秒（約 2.1 ミリ秒）
  以内が要るので、実時間の 4 分の 1 程度の速さになる。
  格子の走査をキャッシュに乗りやすい並びに変えれば改善の余地がある。
- HUD の EFF は実効倍率を整数に切り捨て、下限を 1 にしている。上限付近では実際は 1 倍を下回る。
- 序盤は実寸だと点にしか見えないため、個数が 30 個を下回る間だけ表示上の半径を
  大きくしている。当たり判定には影響しない。
- ボールの回転は扱っていない。すべて同じ大きさの円としている。
- 初期個数は 8192 まで。それ以上は撒く段階で密になりすぎる。
- 乱数の種を固定するオプションが無いため、同じ結果を再現できない。
